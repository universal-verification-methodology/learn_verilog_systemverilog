[Slide 31] Protocol and design detail: Modport Expressions (2009). Use: When the same interface is used with different signal subsets or derived signals; check tool support for exact syntax. Benefit: Fewer duplicate interface definitions; clearer connection contract. From MODULE5 Topics Covered — protocol/design depth.

[Slide 32] Protocol and design detail: Virtual Interface (2009). Design: Rarely used in RTL; RTL typically connects to a concrete interface instance. Verification: Common in UVM and other OOP testbenches; allows one driver class to work with any instance of the interface. From MODULE5 Topics Covered — protocol/design depth.

[Slide 33] Protocol and design detail: Integer Types and Sizes. byte, shortint, int, longint: 8, 16, 32, 64 bits; signed by default. byte unsigned, int unsigned: Unsigned variants. Clarifications in 2012: Representation and conversion rules; use in RTL for constants and parameters. From MODULE5 Topics Covered — protocol/design depth.

[Slide 34] Protocol and design detail: Operators Added or Clarified. inside: Already in 2005; 2009/2012 clarify set membership and use with ranges. Wildcard equality ==?: X/Z in the right-hand side act as “don’t care” in comparisons. Set membership and case (inside): Used in case statements and constraints; semantics clarified in 2012. From MODULE5 Topics Covered — protocol/design depth.

[Slide 36] Protocol and design detail: Array Assignment and Ordering. Packed vs unpacked: Assignment rules and ordering (row-major, etc.) are clarified. Array copy: Whole-array assignment and copying; compatibility of dimensions. Use in RTL: Multi-dimensional arrays (e.g. memories) and parameterized dimensions; follow tool-supported subset for synthesis. From MODULE5 Topics Covered — protocol/design depth.

[Slide 37] Protocol and design detail: String Methods. Strings: string type; methods such as .len(), .substr(), .atoi(), etc. (as defined in 2012). Use in RTL: Rare (strings are mainly for messages and file I/O in testbenches). Use in testbenches: Logging, report generation, file names. From MODULE5 Topics Covered — protocol/design depth.

Use in RTL: Immediate assertions for invariants (e.g. one-hot, valid encodings); concurrent assertions often in bind...

[Slide 39] Protocol and design detail: Checker (2012). checker: A reusable unit that can contain assertions, assumptions, coverage, and helper logic; can be instantiated in design or testbench. Use: Encapsulate a set of properties (e.g. protocol rules) and reuse across modules or hierarchies. Design: Checkers can be bound to RTL modules; they do not change RTL functionality, only add checking. Synthesis...

[Slide 40] Protocol and design detail: Compilation Unit. Compilation unit: The scope of one or more source files compiled together (tool-defined). $unit: The compilation-unit scope; declarations in $unit are visible across the unit without import. Best practice: Prefer packages and explicit import over $unit to avoid hidden dependencies and name clashes. From MODULE5 Topics Covered — protocol/design depth.

[Slide 41] Protocol and design detail: Package and Import. Import: import pkg::* or import pkg::item; 2012 clarifies visibility and search order. Use: Keep shared types and functions in packages; import where needed; avoid relying on $unit for new code. From MODULE5 Topics Covered — protocol/design depth.

[Slide 74] Next section: Common pitfalls.

[Slide 75] Assuming 2009/2012 Features in an 2005-Only Flow. Mistake: Using virtual interface, checker, or 2012 array methods when the project or tool is 1800-2005 only. Reality: Compile or elaboration errors; or undefined behavior. Correct: Confirm project standard and tool revision; use only features of that revision. Why: Backward compatibility is 2005→2009→2012; tools may not implement all newer...

[Slide 76] Virtual Interface in RTL. Mistake: Using a virtual interface in synthesizable RTL. Reality: Virtual interfaces are for dynamic binding (testbench); not for hardware. Correct: Use concrete interface instances in RTL; use virtual interface only in testbench classes. Why: Synthesis does not support virtual interface; it is a simulation construct.

[Slide 77] Checker Synthesis. Mistake: Expecting a checker to be synthesized like a module. Reality: Checkers are for assertion/coverage; typically not synthesized. Correct: Use checkers for verification; keep RTL in modules. Why: Checker semantics are for checking, not for netlist generation.

[Slide 78] Array Methods in RTL. Mistake: Using dynamic array or queue methods (e.g. .push_back) in synthesizable RTL. Reality: Many such methods are not synthesizable or are tool-specific. Correct: In RTL use fixed-size or parameterized arrays and indexing; use methods in testbenches or checkers. Why: Synthesis subset of SystemVerilog is smaller than the full language.

[Slide 79] $unit vs Package. Mistake: Putting shared types or functions in $unit and relying on compilation order. Reality: $unit visibility and order are tool-dependent; can cause subtle bugs. Correct: Put shared items in packages; use explicit import. Why: Packages give a clear namespace and import order; 2012 clarifies compilation unit but packages remain best practice.
